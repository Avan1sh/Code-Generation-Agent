The one question this project answers

When a model writes bad code you have two cheap options: run it again and hope (resampling), or show it the error and ask it to reason about the fix (reflection). Reflection costs more, one extra call per failed attempt. The project exists to find out whether that extra spend buys anything.

That is why there are three methods, not one. single_shot is the floor. best_of_n is a deliberately unfair oracle ceiling. The agent sits between them, and its position is the answer.

The finding, stated honestly

On the 30-problem run the agent scored 30/30 against a 26/30 baseline. Decomposed, only +1 of those 4 came from the correction step. The other three were temperature-0 sampling variance and one rate-limited baseline call. The harness's own noise floor measures about 3 problems, so +1 is not interpretable. The defensible claim is that the loop did not hurt, not that it helped.

Everything below exists to make that sentence survive questioning.

Mental model

Five nodes, one bounded loop

test_gen ──▶ generate ──▶ static_check ──pass──▶ execute ──pass──▶ END
                 ▲              │                    │
                 │          fail│               fail │
                 │              ▼                    ▼
                 └────────── reflect ◀───────────────┘
                        (only while attempts remain)

Read it as a pipeline with one cycle. Work flows left to right; failure sends it back through reflect, which is the only node that exists to explain rather than produce.

NodeLLM?What it does
test_genrarelyLoads hand-written tests from disk. Only calls the model when a prompt has no canonical tests, which is the ad-hoc path.
generateyesProduces code. On retry it carries the prior code, the concrete failure evidence, and the diagnosis.
static_checknoast parse, pyflakes, and 8 regex rules for v1 anti-patterns. Free, deterministic, runs before any sandbox spend.
executenoRuns the tests under pytest in a resource-limited subprocess.
reflectyesOne call producing a root cause and a fix direction. Explicitly forbidden from writing code.
Why test_gen runs once, outside the loop Regenerating tests per attempt would let the success criterion drift under a failing solution. The target has to hold still or the measurement means nothing.
Why reflect may not emit code If it wrote code it would just be a second generator, and the eval could no longer isolate whether the reflection step contributes anything. Separating "what went wrong" from "write it again" is the entire hypothesis under test.
Why static_check sits before execute It is free and deterministic. Rejecting v1 syntax here means never spending a sandbox run on code already known to be wrong, and it hands the reflector precise evidence instead of a stack trace.

baselines/ — the comparisons

single_shot.py52 lines

One generation, one test run, no correction. The number the agent must beat.

The critical detail It imports SYSTEM_PROMPT from the generator and uses temperature 0, so it is prompt-identical to the agent's attempt 1. If it were not, any measured gap would confound "the loop helped" with "the retry prompt was just better".

best_of_n.py74 lines

N independent samples at temperature 0.8. Passes if any sample passes.

Why an unfair baseline is on purpose Reporting pass@N requires knowing which sample passed, which at inference time means already having the tests. It is not deployable. It is included because it is compute-matched, which makes the real question answerable: at equal budget, does directed correction beat undirected resampling? It is also what tells you when the eval itself has stopped working.

eval/ — the measurement

run_eval.py219 lines

Runs all three methods over the problem set in one process and writes one JSON line per (problem, method). It aggregates nothing.

Why measurement and analysis are separate files The raw record survives a wrong analysis, and numbers can be recomputed without re-spending API budget. It also means a bug in the summary can never quietly corrupt the evidence.

analyze.py189 lines

Turns a run file into counts: headline, paired per-problem deltas, attempt distribution, per-category breakdown, token cost.

Three rules it enforces in code Raw counts always accompany rates. Errored rows count as failures rather than being dropped, because a dropped row shrinks the denominator and inflates every rate. And it refuses to print a summary at all when there is no data behind it.

partial_credit.py153 lines

Re-executes the solutions already stored in a run file and counts individual assertions. Zero API cost.

Why it exists At n=30 a binary outcome can only express differences of 3.3 points. The 185 assertions underneath were already paid for, so the finer signal just needs reading out. This is also the tool that caught a bug in the eval set itself.

problems/ — the eval set

40 problems, 185 assertions, 7 easy / 12 medium / 21 hard. Each directory holds four files:

The eval set validates itself

tests/test_problem_set.py asserts three things for all 40 problems, with no API key: the reference solution passes its own tests in the real sandbox; the reference passes the static gate, which proves the v1 detector has no false positives that would reject correct code; and no prompt leaks a v2 API name, which would turn the eval into an instruction-following test instead of a knowledge test.

state.py

Why the state is typed, and one subtlety

AgentState is a Pydantic v2 model, not a TypedDict and certainly not a bare dict. Every node transition is runtime-validated. It is also thematically consistent: the agent's own state is a v2 model in a project about v2 correctness. 

class AgentState(BaseModel):
    problem: Problem
    max_attempts: int = 3
    attempt_number: int = 0

    generated_code: str | None = None
    test_code: str | None = None
    static_check_result: StaticCheckResult | None = None
    execution_result: ExecutionResult | None = None
    reflection: str | None = None

    history: Annotated[list[AttemptRecord], operator.add] = ...
    status: Status = "in_progress"
The reducer on history Annotated[list[AttemptRecord], operator.add]. LangGraph merges each node's partial return into state, so without an explicit reducer a later node's return would clobber history instead of extending it.
Who commits a history record Exactly one node per attempt. If the static gate fails, static_check owns the record and execution stays None. If it passes, execute owns it. That is how the analysis distinguishes a static rejection from a test failure, and it is why neither node double-counts.
What reflection means on a record It is the diagnosis that guided this attempt, not a diagnosis of it. That lets analysis ask "did this diagnosis lead to a fix?" by reading the next record.
What is deliberately not in state A visitor's API key. State is serialised into history records and run files, so a credential placed there would leak into logs and saved output. The hosted demo carries it in a ContextVar instead.
graph.py

How the loop is proven to stop

This is the claim most worth being able to defend, so it rests on three things in order of importance.

1. Node-level guards

static_check_node and executor_node each compare attempt_number >= max_attempts themselves and write a terminal status. The conditional edges only read that status. Routers never decide termination.

2. A monotonic counter

attempt_number is incremented by generate on every pass and is never decremented anywhere, so the guard in (1) is guaranteed to fire within max_attempts generations regardless of what the model outputs.

3. recursion_limit as a backstop only

Set to max_attempts * 4 + 10, above the worst case, so hitting it means a wiring bug. It is explicitly not the guarantee: it raises GraphRecursionError, a crash, rather than producing a clean terminal state.

This is tested, not asserted

tests/test_graph_termination.py runs the real graph with a stub LLM that always emits broken code, the worst case of a model that never self-corrects. It checks the bound holds at max_attempts 1, 2 and 3, on both the static-failure and test-failure paths, that a success short-circuits immediately, and that no reflection call is paid for after the final attempt. No API key required.

sandbox.py

Running untrusted code

Generated code is never passed to exec() or eval(), not even in a throwaway check. It is written to a temporary directory and run under pytest in a subprocess.

ControlMechanismWhere it applies
Wall-clock timeoutsubprocess timeoutevery platform
Address spaceRLIMIT_ASPOSIX only
CPU timeRLIMIT_CPUPOSIX only
Process countRLIMIT_NPROCPOSIX only
Networknonenowhere
Why the memory ceiling is generous, not tight RLIMIT_AS caps virtual address space, not resident memory. CPython plus pydantic-core reserve far more address space than they make resident, so a ceiling tuned to "how much should a solution need" rejects perfectly good solutions. It exists to stop unbounded allocation, not to enforce a budget.
Why it must sit below the container budget On a 512MB instance a 2048MB ceiling protects nothing: the child grows until the container is killed. SANDBOX_MEMORY_MB is set to 300 in production for exactly this reason.
Why the timeout is configurable 10s suits a developer machine where the probe takes 1.7s. On shared hosting the same probe takes 17.1s, and valid solutions then report timed_out, which reads as the model writing infinite loops. Hardware-dependent values must be settable per environment.
Why concurrency is capped at one run preexec_fn runs between fork and exec, and forking from a multi-threaded process to set rlimits is the classic deadlock. FastAPI runs sync endpoints in a threadpool, so a semaphore keeps the fork quiet.
verify_sandbox_health, the pattern worth stealing

Before the eval spends anything, known-good pydantic code is run through the sandbox under the configured limits. If ceilings are too tight for the interpreter itself, every problem fails, the eval reports 0 across all three methods, and it looks like catastrophic model failure. The check turns that into a loud, self-describing error. The same idea produced verify_llm_available() after a retired model ID caused exactly that outcome.

Methodology

How the measurement is built

This is the part that matters most, and the part most likely to be probed.

One process, one model snapshot

All three methods run in the same invocation against the same problem set. A baseline measured in a different run against a different model snapshot is not a baseline. Provider-side changes alone move the number, which stopped being hypothetical when Groq retired two model IDs mid-project.

The oracle is what detects a broken eval

If best_of_n sits at the floor, no method could have scored higher and the eval has no discriminating power. That is how Run 1 was identified as measuring nothing. Without an oracle a null result is a shrug; with one it is a diagnosis.

Paired deltas, not just aggregates

A net +0 can hide the loop fixing one problem and breaking another. That is exactly what happened in Run 2, so analyze.py prints "fixed by the loop" and "broken by the loop" separately.

The noise floor is measured, not assumed

single_shot and the agent's attempt 1 send an identical prompt to an identical model at temperature 0. They still disagreed on 3 of 30 problems, because provider-side batching makes temperature 0 non-deterministic. Any A/B difference smaller than about 3 problems at this n sits inside the harness's own instability.

Cost is measured in tokens, not calls

A reflection call carries the failing code plus a pytest traceback, so it is far more expensive than a first-attempt generation. "54 calls" hides that. The headline cost figure is tokens per solved problem, because a method can look cheap in total while being expensive per unit of work delivered.

The result that does clear the noise floor

self_correct costs 812 tokens per solve against the baseline's 805, because the loop only spends when it fails. best_of_n costs 2,347, roughly 2.9x, and scored lower. Undirected resampling is the expensive strategy. That gap is far outside the noise floor, so it is a claim you can actually make.

Where the technique stops working

All three of the agent's Run 3 solves landed on attempt 2, none on attempt 3. Reflection reliably repairs syntactic v1 to v2 errors on the first correction and reliably fails on semantic ones after. In Run 2 the oracle sat only one problem above the floor, which means failures were systematic rather than stochastic: neither resampling nor reflection addresses a knowledge gap.

Chronology

The bug log

These are in the order they were found, because each one shaped what came after. Nearly all of them are bugs in the instrumentation, not the agent, and that is the point: every one produced a failure that looked like something else.

01

The model tier was too weak to measure anything

Run 1 returned 1/12, 1/12, 0/12. Read as a headline it says self-correction made things worse. The oracle ceiling was also 1/12, so no method could have scored higher.

LessonAn eval with no discriminating power produces numbers that look like findings. The ceiling is what tells you the measurement is broken.
02

A canonical test did not test what it claimed

pyd_003's stored solution passed every assertion while the pipeline recorded it as failed_static. The code used class Config:, which Pydantic v2 still honours for backwards compatibility, so it populates model_config exactly as ConfigDict would. A test asserting on model_config passes for v1-style and v2-style code alike.

LessonWhen two ground-truth signals disagree about the same code, one of them is wrong. Here the gate was right and the test was too weak. The fix asserts not hasattr(Model, "Config"), and it was checked that it changed no headline number before being applied.
03

A retired model ID produced a fake 0/30

Groq retired both Llama models mid-project. Two full runs recorded 90/90 errored rows and the analysis printed 0/30 for all three methods, which reads exactly like catastrophic model failure.

LessonAny condition that makes every measurement fail identically must be checked before the measurement, not diagnosed after. Hence verify_llm_available(), one call, aborts with exit 3.
04

A health check that could never fail

An edit placed an early return above the raise in verify_sandbox_health(). The guard reported healthy no matter what. It was caught only because an existing test failed, and that test was itself flaky: it used a 1-second budget that passed on a warm machine, so it had been green while the check was broken.

LessonA guard that cannot fail is worse than no guard, because it is trusted. The test now uses a zero budget, which is deterministic, plus a regression test asserting the healthy path returns a real measurement.
05

A too-short timeout impersonated infinite loops

On the free hosting tier every attempt reported timed_out. Render allocates a fraction of a CPU, and the 10s default was too short for interpreter startup plus a pydantic import. Valid solutions were being recorded as timeouts.

LessonHardware-dependent constants must be configurable and, more importantly, measurable. /api/status now reports the probe duration next to the configured timeout, so the value is set from data. Locally 1.7s, in production 17.1s.
06

A stray yield emptied every API response

The demo returned HTTP 200 with zero bytes. An orphan yield left inside the endpoint by a line-based edit made it a generator function, and FastAPI 0.141 streams generator endpoints as application/jsonl. A return JSONResponse(...) inside a generator yields nothing.

LessonThe whole test suite stayed green because no test asserted on a response body. Every signal pointed elsewhere: 200 not 5xx, worker never restarted, the status endpoint fine. The instrumentation added while chasing it, a boot_id, is what refuted the leading hypothesis rather than confirming it.
Preparation

Questions you should expect

Each answer names the evidence to point at. Open one and try answering before reading.

Your agent scored 30/30. Isn't that a great result?

No, and the decomposition is the reason. 29 of those 30 solves landed on attempt 1, which is prompt-identical to the baseline and runs no reflection at all. Of the four problems the baseline missed, one was a rate limit, two were sampling variance, and exactly one was repaired by the correction step.

So the loop contributed +1 out of 30, and the harness noise floor is about 3 problems. It is not interpretable.

Point at: the decomposition table, and analyze.py's attempts-used breakdown.
How do you know temperature 0 is not deterministic?

Measured it. single_shot and the agent's attempt 1 send an identical prompt to an identical model at temperature 0. They disagreed on 3 of 30 problems, roughly a 10 percent per-problem rate, because provider-side batching changes floating-point reduction order.

That number is the floor beneath which this harness cannot resolve anything, which is why the +1 is reported as uninterpretable rather than as a small win.

Point at: Run 3, attempt-1 count 29 versus single_shot 26.
Why include a baseline you admit is unfair?

Two reasons. It is compute-matched, so it answers whether directed correction beats undirected resampling at equal budget. And it is the only thing that tells you when the eval itself has stopped working.

In Run 1 the oracle sat at 1/12, the same as the floor. That immediately says no method could have scored higher and the eval measured nothing. Without it, a null result is a shrug instead of a diagnosis.

Point at: Run 1, and the Run 2 oracle sitting one problem above the floor.
Prove the retry loop terminates.

Three layers. Node-level guards compare attempt_number >= max_attempts and write a terminal status; routers only read it. attempt_number is incremented on every pass and never decremented, so the guard is guaranteed to fire. recursion_limit is a backstop only, and deliberately not the guarantee, because it raises rather than terminating cleanly.

It is tested with a stub model that never succeeds, at max_attempts 1, 2 and 3, on both failure paths.

Point at: tests/test_graph_termination.py, 5 tests, no API key needed.
How do you know your eval set is not just broken?

Every problem ships a hand-written reference solution, and CI asserts that it passes its own tests in the real sandbox, that it passes the static gate (so the v1 detector has no false positives that would reject correct code), and that no prompt leaks a v2 API name.

That check has already earned its place twice: it caught a test guard of mine that rejected my own correct answer, and the partial-credit pass caught a canonical test that did not test what it claimed.

Point at: tests/test_problem_set.py, and bug 02 in the log.
You run model-written code. Is that safe?

Never exec() or eval(), not even in throwaway checks. It runs under pytest in a subprocess with a wall-clock timeout everywhere, plus RLIMIT_AS, RLIMIT_CPU and RLIMIT_NPROC on POSIX. Those were a design claim until CI on Linux began running the tests that exercise them, and the workflow fails the build if those tests skip, since a skipped test still exits 0.

The honest gap: no network isolation. Generated code could open a socket. Container isolation is the outer boundary. That guarantee is unproven because it does not exist, not because it is untested.

Point at: the CI step "POSIX sandbox tests must RUN, not skip".
What would you do differently or next?

The eval set no longer discriminates at this model tier: 26/30 zero-shot leaves four problems of headroom. Only two of ten deliberately harder problems worked, and both shared one property, which is the generative principle worth reusing: the obvious answer looks correct, is silently accepted, and silently does nothing. One model wrote ConfigDict(serialize_as_any=True), which is not a real key, but ConfigDict is a TypedDict, so it is accepted, stored, and has no effect.

Beyond that: repeated runs for seed variance, since every number is currently a single point estimate. I would not keep tuning the eval until a favourable number appears, which is the exact failure this project was built to avoid.

Point at: Run 4, and the pyd_032 and pyd_037 analysis.
What is the weakest part of this project?

That the central question is unanswered. n=30 with a 3-problem noise floor cannot resolve the effect being measured, and three of four calibration attempts landed outside the measurable band.

What I would defend is that the project knows this and says so, rather than reporting 30/30 and moving on. The infrastructure is finished; the science is honest but inconclusive, and those are different statements.
